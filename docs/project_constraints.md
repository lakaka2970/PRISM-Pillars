## 1. 项目构建目的

### 1.1 问题陈述

4D 毫米波成像雷达在自动驾驶 3D 目标检测中面临三个核心挑战：

| 挑战 | 描述 | 现有方案的不足 |
|------|------|--------------|
| **时序证据不可靠** | 历史雷达回波受自车运动、Doppler 模糊、多径效应影响，确定性补偿产生目标拖影和错误 Pillar 分配 | RadarPillars 仅做朴素多帧累积；DoppDrive 用硬阈值剔除，丢失有效信息 |
| **不确定性不建模** | Doppler 只直接约束径向运动，切向方向天然不可观，但现有方法将历史点视为确定性几何点 | 各向同性高斯过于粗糙；R4Det 用 DCN 隐式学习对齐，缺乏物理可解释性 |
| **精度-效率权衡** | 时序融合带来额外计算，需要在精度提升和推理延迟之间取得可部署的平衡 | RadarNeXt 无时序建模；PRISM 原方案未考虑实时性 |

### 1.2 项目目标

构建 **PRISM-Pillars-RF**：一个在精度上显著超越 RadarPillars 基线、在边缘设备推理效率上对标 RadarNeXt 的 4D 雷达 3D 目标检测器。

**核心方法论**：Correct-then-Refine（先纠正时序证据，再增强空间表征）

```
历史雷达回波 → 概率证据建模（各向异性不确定性 + 自监督可靠性）
           → 可靠性感知局部时序融合
           → 可重参数化骨干 + 轻量可变形颈部
           → 3D 检测输出
```

### 1.3 项目边界

**本项目是（In Scope）：**
- 基于 OpenPCDet 框架的 4D 雷达 3D 目标检测模型
- 以概率建模为核心的时序证据融合方法
- 可重参数化的高效骨干网络设计
- View-of-Delft (VoD) 和 TJ4DRadSet 数据集上的训练与评估
- 从训练态到部署态的完整工具链

**本项目不是（Out of Scope）：**
- 激光雷达点云或多模态融合检测
- 端到端自动驾驶规划或控制
- 传感器标定或数据采集
- 通用的 2D 检测或分割任务
- 不在 VoD/TJ4DRadSet 之外的零样本泛化保证

## 3. 准确性约束（精度验收指标）

### 3.1 主指标定义

| 指标 | 定义 | 计算方式 |
|------|------|---------|
| **mAP** | 三个类别的 3D Average Precision 均值 | (AP_Car + AP_Ped + AP_Cyc) / 3 |
| **AP_Car** | 汽车类 3D AP, IoU=0.50, R40 | P-R 曲线下面积 @ 40 召回点 |
| **AP_Ped** | 行人类 3D AP, IoU=0.25, R40 | P-R 曲线下面积 @ 40 召回点 |
| **AP_Cyc** | 骑行者类 3D AP, IoU=0.25, R40 | P-R 曲线下面积 @ 40 召回点 |
| **EAA** | Entire Annotated Area (全标注区域) | 不限制距离/角度的全域评估 |

### 3.2 对标基线

**主基线：RadarPillars (IROS 2024, Gillen et al.)**

| 指标 | RadarPillars 论文值 | 本仓库复现值 | 验收参照基准 |
|------|-------------------|-------------|-------------|
| mAP | 50.70 | 48.76 | **49.00** (取复现值, 因硬件/数据版本差异) |
| Car AP@0.50 | 41.10 | 36.29 | **36.50** |
| Ped AP@0.25 | 38.60 | 41.09 | **39.00** |
| Cyc AP@0.25 | 72.60 | 68.90 | **69.00** |

> **说明**：论文报告值与本地复现值存在差异（主要源于 GPU 型号、PyTorch 版本、数据预处理细节），验收基准取复现值四舍五入。若后续复现精度提升，验收基准应同步更新但不降低。

### 3.3 精度验收阈值

#### 3.3.1 主验收线（PRISM-Pillars-RF-S, C=32, AnchorHead）

| 指标 | 基线值 | 最低要求 | 目标值 | 卓越值 | 测量条件 |
|------|--------|---------|--------|--------|---------|
| **mAP** | 49.00 | ≥ 50.00 (+1.0) | ≥ 51.00 (+2.0) | ≥ 52.00 (+3.0) | EAA, R40, 3 次运行均值 |
| **Car AP** | 36.50 | ≥ 37.50 (+1.0) | ≥ 38.50 (+2.0) | ≥ 40.00 | IoU=0.50 |
| **Ped AP** | 39.00 | ≥ 40.00 (+1.0) | ≥ 41.50 (+2.5) | ≥ 43.00 | IoU=0.25 |
| **Cyc AP** | 69.00 | ≥ 70.00 (+1.0) | ≥ 72.00 (+3.0) | ≥ 74.00 | IoU=0.25 |

**最低通过条件**：mAP ≥ 50.00 且 Car/Ped/Cyc 三个类别中至少两个类别不低于基线。

#### 3.3.2 精度版验收线（PRISM-Pillars-RF-C, C=48, CenterHead）

| 指标 | 基线值 | 最低要求 | 目标值 | 卓越值 |
|------|--------|---------|--------|--------|
| **mAP** | 49.00 | ≥ 51.50 (+2.5) | ≥ 53.00 (+4.0) | ≥ 54.50 (+5.5) |
| **Car AP** | 36.50 | ≥ 39.00 (+2.5) | ≥ 40.50 (+4.0) | ≥ 42.00 |
| **Ped AP** | 39.00 | ≥ 42.00 (+3.0) | ≥ 43.50 (+4.5) | ≥ 45.00 |
| **Cyc AP** | 69.00 | ≥ 72.00 (+3.0) | ≥ 74.00 (+5.0) | ≥ 75.00 |

### 3.4 统计显著性要求

| 检验项 | 方法 | 阈值 |
|--------|------|------|
| **主指标显著性** | 配对 bootstrap 检验 (1000 次重采样, α=0.05) | p < 0.05 |
| **多次运行一致性** | 不同随机种子 (42, 666, 1024, 2023, 3407) 至少 3 次独立训练 | mAP 标准差 ≤ 0.30 |
| **消融实验可靠性** | 每项消融至少 2 次运行，报告均值和标准差 | — |
| **性能提升的鲁棒性** | 在 validation set 上 ΔmAP 的 95% 置信区间下限 ≥ 0.5 | CI_lower ≥ 0.5 |

**统计检验流程**：
```
1. 使用 3 个不同随机种子分别训练基线 (RadarPillars) 和 PRISM-Pillars-RF
2. 对每对 (基线, PRISM) 结果，在 val set 上逐帧计算 AP 差异
3. 1000 次 bootstrap 重采样计算 ΔmAP 的 95% 置信区间
4. 若 CI 下限 ≥ 0.5 且 p < 0.05，判定为显著提升
```

### 3.5 负面约束（不允许的精度代价）

| 约束 | 阈值 | 说明 |
|------|------|------|
| 任一类 AP 下降 | ≤ -1.5 | 若 Car/Ped/Cyc 任一类 AP 下降超过 1.5，即使 mAP 提升也需重新审查 |
| 远距离退化 | ≤ -2.0 @ >30m | 30m 以外的目标 AP 不得显著恶化 |
| 小目标退化 | ≤ -2.0 | 行人/骑行者 AP 不得因时序融合导致模糊化而恶化 |

## 4. 效率约束（边缘部署验收指标）

### 4.1 对标基线

**效率基线：RadarNeXt (EURASIP 2025, Jia et al.)**

| 指标 | RadarNeXt 报告值 | 验收基准 |
|------|-----------------|---------|
| RTX A4000 FPS | 67.10 | ≥ 60.4 (90%) |
| Jetson AGX Orin FPS | 29.03 | ≥ 26.1 (90%) |
| 参数量 (部署态) | 未明确 (估计 ~0.3M) | ≤ 0.6M |
| GFLOPs | 未明确 | ≤ 3.0 |

> **说明**：RadarNeXt 报告的 FPS 值基于其完整的 RepDWC + MDFEN 架构但不含时序模块。PRISM-Pillars-RF 在此基础上增加了时序证据建模（STER + DAUT + RAPR + CRLF），因此允许效率最多降低 10%，但不得低于 RadarNeXt 的 90%。

### 4.2 推理效率验收阈值

| 指标 | 平台 | 最低要求 | 目标值 | 卓越值 | 测量条件 |
|------|------|---------|--------|--------|---------|
| **FPS** | RTX A4000 | ≥ 60.4 | ≥ 64.0 | ≥ 67.0 | FP32, batch=1, 部署态, CUDA sync |
| **FPS** | Jetson AGX Orin | ≥ 26.1 | ≥ 28.0 | ≥ 29.0 | FP16, batch=1, 部署态, TensorRT (若可用) |
| **P95 延迟** | RTX A4000 | ≤ 23.0 ms | ≤ 21.0 ms | ≤ 18.0 ms | 1000 次迭代, 100 次预热 |
| **P99 延迟** | RTX A4000 | ≤ 30.0 ms | ≤ 25.0 ms | ≤ 22.0 ms | 1000 次迭代, 100 次预热 |
| **GPU 显存** | RTX A4000 (16GB) | ≤ 6 GB | ≤ 4 GB | ≤ 3 GB | batch=1, 训练态 |

### 4.3 分模块延迟预算

时序模块的加入不能无限制增加延迟。各模块延迟预算分配如下：

| 模块 | 延迟预算 (ms) | 占比上限 | 说明 |
|------|-------------|---------|------|
| 数据加载 + 自车对齐 | ≤ 3.0 | 18% | 含序列加载和坐标系变换 |
| 点特征编码 + VFE + PillarAttention | ≤ 3.0 | 18% | 当前帧确定性编码 |
| **STER + DAUT + RAPR (PRISM)** | ≤ 5.0 | 28% | 时序证据建模核心（最重模块） |
| **CRLF (时序融合)** | ≤ 2.0 | 11% | 局部注意力 + 门控融合 |
| RepDWC 骨干网络 | ≤ 3.0 | 18% | 部署态融合后单路径 |
| Lite-MDFEN 颈部 | ≤ 2.5 | 14% | 单 DCNv3 + 旁路 |
| 检测头 | ≤ 3.0 | 18% | AnchorHead 或 CenterHead |
| **端到端总计** | **≤ 18.0** | — | 输入点云到输出检测框 |

> 若总延迟超过 18.0 ms (即 FPS < 55.6)，则必须进行延迟优化或考虑模块裁剪。

### 4.4 延迟测量规范

```
测量环境：
  - CUDA 同步：每次推理前后均执行 torch.cuda.synchronize()
  - 预热：100 次推理后开始计时
  - 测量次数：≥ 1000 次
  - 排除项：不包含模型加载时间、不包含 Python 开销（仅算子耗时）
  - 精度：FP32 (主报告) + FP16 (补充报告)
  - Batch size：1（延迟优先场景）和 4（吞吐优先场景）

测量脚本：
  python tools/benchmark_latency.py \
      --cfg_file tools/cfgs/vod_models/prism_pillars_rf_s.yaml \
      --ckpt deploy_models/prism_s_deploy.pth \
      --iterations 1000 --warmup 100
```

## 6. 模块级退出标准

每个从外部引入或新设计的模块都有明确的退出标准。不满足标准的模块必须从最终模型中移除或回退到更简单的替代方案。

### 6.1 退出标准表

| 模块 | 来源 | 退出条件 | 回退方案 | 验证阶段 |
|------|------|---------|---------|---------|
| **RepDWC Backbone** | RadarNeXt | ΔmAP < -0.3 vs Conv2D 骨干 | 退回 BaseBEVBackbone (Conv2D) | P5 |
| **Lite-MDFEN** | RadarNeXt | ΔmAP < 0.5 **或** ΔLatency > +10% | 移除 MDFEN，仅用 RepDWC 骨干 | P6 |
| **STER (可靠性)** | 本项目 | 训练不稳定 **或** ΔmAP < 0.3 | 固定 q=1 或解析 q_i = exp(-η₁d - η₂e) | P3 |
| **DAUT (可学习 Σ)** | 本项目 | 训练不稳定 **或** σ 频繁触及边界 | 固定 σ_r=0.10+0.15·|Δt|, σ_t=0.50+0.50·|Δt| | P4 |
| **RAPR (概率路由)** | 本项目 | ΔmAP < 0.3 vs 确定性最近邻路由 | 退回确定性 Pillar 分配 | P2 |
| **CRLF (时序融合)** | 本项目 | ΔmAP < 0.5 **或** ΔLatency > +15% | 退回朴素拼接或简单平均 | P2 |
| **CenterHead** | OpenPCDet | ΔmAP < 0.5 **或** ΔLatency > +10% vs AnchorHead | 退回 AnchorHeadSingle | P7 |

### 6.2 退出判定流程

```
1. 在验证集上分别评估带有目标模块和不带目标模块的模型
2. 各训练 3 次（不同随机种子），计算 ΔmAP 均值和标准差
3. 若 ΔmAP 均值 - 标准差 < 退出阈值 → 触发退出
4. 若 ΔLatency > 退出阈值 → 触发退出
5. 退出后使用回退方案重新训练完整模型
6. 记录退出决策和依据到实验日志
```

## 7. 训练过程约束

### 7.1 训练配置约束

| 配置项 | 约束 | 原因 |
|--------|------|------|
| 优化器 | Adam OneCycle (与基线一致) | 保证对比公平 |
| 混合精度 | 默认 FP32，仅在最终验证阶段允许 FP16 | 避免训练不稳定引入的偏差 |
| 批次大小 | 有效总 batch ≥ 8 (跨所有 GPU) | 保证 BN 统计量稳定 |
| 训练轮数 | P0 基线 60 轮，PRISM 80 轮 | 为时序模块提供充分的收敛时间 |
| 学习率预热 | 前 40% 训练步数使用余弦预热 | 时序模块初期不稳定，需缓慢升温 |
| 梯度裁剪 | max_norm = 10 | 防止概率模块梯度爆炸 |
| 随机种子 | 主实验固定 666，显著性实验使用 3 种不同种子 | 保证可复现 + 统计检验 |

### 7.2 分阶段训练约束

| 阶段 | 约束 | 成功标准 | 阻塞后续阶段？ |
|------|------|---------|-------------|
| P0 | 必须严格复现 RadarPillars 基线 | \|ΔmAP\| ≤ 1.0 vs 论文值 | **是** — P0 不通过则不得继续 |
| P1 | 必须验证 anisotropic > isotropic > deterministic 排序 | 严格单调递增 | **是** — 违反物理直觉则方案不可行 |
| P2 | 时序融合局部半径 ≤ 5, TopK ≤ 32 | O(p·K_t) < O(p²) | 否 — 可调参继续 |
| P3 | λ_rel 必须在预热阶段线性递增 | 收敛稳定 | 否 — 可调参继续 |
| P4 | 可学习 σ 必须在物理边界内 | σ_r ∈ [0.03, 0.60], σ_t ∈ [σ_r, 2.00] | 否 — 可回退固定值 |
| P5 | RepDWC 部署态等价性 max_diff < 1e-4 | 等价性测试通过 | 否 — 可回退 Conv2D |
| P6 | MDFEN ΔLatency ≤ 10% | 延迟不超标 | 否 — 可移除 |
| P7 | CenterHead ΔLatency ≤ 10% | 延迟不超标 | 否 — 可回退 AnchorHead |
| P8 | 微调 LR ≤ 1e-4, 轮数 ≤ 20 | 不破坏已学到的表示 | — |

| 阶段 | 单次训练时长 (A4000) | 预计训练次数 | 总 GPU 小时 |
|------|-------------------|------------|------------|
| P0 (基线复现) | ~3 h | 5 次 (不同帧数/种子) | ~15 h |

| P2 (局部融合) | ~6 h | 3 次 | ~18 h |

## 8. 数据与评估约束

### 8.1 数据集约束

| 约束项 | 要求 |
|--------|------|
| 主数据集 | View-of-Delft (VoD) radar_5frames |
| 辅助数据集 | TJ4DRadSet（用于跨数据集泛化验证） |
| 数据划分 | **序列级划分** (SEQUENCE_LEVEL_SPLIT=true)，严禁同序列帧跨 train/val |
| 历史帧数 | S 版 3 帧，C 版 5 帧 |

| 体素尺寸 | [0.16, 0.16, 5.0]（与 RadarPillars 一致） |

### 10.2 验收判定规则

| 场景 | 判定 |
|------|------|
| 全部约束满足 | ✅ **通过** — 项目达成目标，可撰写论文 |
| 精度约束满足, 效率约束差 ≤ 5% | ⚠️ **条件通过** — 需在论文中讨论效率差距原因和优化计划 |
| 精度约束差 ≤ 0.5 mAP, 效率约束满足 | ⚠️ **条件通过** — 需额外消融分析精度不足的原因 |
| 精度差 > 0.5 mAP 或效率差 > 5% | ❌ **不通过** — 需调整方案后重新验收 |
| 模块触发退出但整体精度仍达标 | ✅ **通过** — 模块退出是预期行为，在论文中报告即可 |

## 11. 判定矩阵

### 11.1 精度-效率四象限

```
              效率 ↑ (满足)
               │
   ⚠️ 条件通过  │  ✅ 通过
   (分析效率)   │  (完美达成)
               │
  ─────────────┼─────────────→ 精度 → (满足)
               │
   ❌ 不通过   │  ⚠️ 条件通过
   (重新设计)  │  (分析精度)
               │
               │ 效率 ↓ (不满足)
```

### 11.2 最终判定矩阵

| 精度 (mAP) | 效率 (FPS) | 复杂度 | 模块退出 | 最终判定 |
|-----------|-----------|--------|---------|---------|
| ≥ +2.0 | ≥ 90% | ✓ | 0 | ✅ 卓越 |
| ≥ +1.0 | ≥ 90% | ✓ | ≤ 1 | ✅ 通过 |
| ≥ +1.0 | 85-90% | ✓ | ≤ 2 | ⚠️ 条件通过 |
| ≥ +1.0 | ≥ 90% | 超标 | ≤ 1 | ⚠️ 条件通过 |
| < +1.0 | ≥ 90% | ✓ | — | ❌ 精度不达标 |
| ≥ +1.0 | < 85% | — | — | ❌ 效率不达标 |
| < +0.5 | < 85% | — | — | ❌ 全面不达标 |
